     desviei) procurando trechos que fazem a mesma coisa com menos código/estrutura, e
     simplificar. Só manter a versão mais complexa se ela resolver algo de verdade
     (funcionalidade ou bug real) que a versão simples não resolveria — não por ser
     "o jeito do tutorial".
   - Fazer essa passada ANTES da Fase 3 (ponteiros/RAII/destruição), já que reescrever
     código é exatamente o tipo de mudança que pode reintroduzir um dangling pointer ou
     quebrar uma ordem de destruição sem querer.

3. Macro de pré-processador onde um constexpr/const resolveria melhor
   - Bug já identificado: MAX_LIGHTS (crs_frameInfo.hpp) foi declarado como
     "#define MAX_LIGHTS 10" dentro de "namespace lve { ... }". Isso funciona, mas é
     enganoso: #define é processado pelo pré-processador, que não entende chaves de
     namespace — a macro vira global no arquivo (e em qualquer outro que incluir esse
     header), não "lve::MAX_LIGHTS" como as chaves sugerem visualmente. Só não deu
     problema ainda porque nenhum outro lugar do projeto usa esse nome.
   - Instrução pra revisão final: procurar todo #define usado como constante (não como
     inclusão condicional de header, esse uso é legítimo) e trocar por
     "constexpr int MAX_LIGHTS = 10;" (ou equivalente) — isso sim respeita namespace de
     verdade, tem tipo, e aparece no debugger/autocomplete do jeito que uma macro nunca
     aparece.

FASE 2 — Otimizações de performance/arquitetura (mudanças mais aditivas)
===============================================================================

4. Auditoria de staging buffer (otimização de memória)
   - Critério: buffers escritos UMA VEZ (ou raramente) e lidos MUITAS VEZES pela GPU
     (vertex buffer, index buffer, malha estática) deveriam usar staging buffer +
     copyBuffer pra ficar em memória DEVICE_LOCAL (mais rápida pra GPU ler).
   - Buffers escritos TODO FRAME pela CPU (ex: um futuro uniform buffer de câmera que
     muda a cada frame) devem continuar em HOST_VISIBLE direto — staging não ajuda
     nesse caso, só adiciona uma cópia extra sem necessidade.
   - Já conferidos: createVertexBuffers (✅ usa staging), createIndexBuffers (✅ usa staging).
   - ✅ Conferido de novo em 2026-10-14: textura também usa staging (CrsBuffer); o UBO,
     escrito todo frame, fica em HOST_VISIBLE com flush — tudo dentro do critério.
   - Conferir também qualquer buffer novo que aparecer depois (uniform buffers,
     texturas, instance data, etc.) contra esse mesmo critério.

5. Layout de dados (cache-friendliness)
   - Preferir estruturas de dados compactas e contíguas em vez de objetos genéricos com
     muitos campos não usados (a lição da comparação UPBGE vs. engine sob medida).

6. Batching de draw calls
   - Agrupar objetos que usam o mesmo pipeline/material em vez de emitir uma chamada de
     desenho separada pra cada um.

7. Culling (frustum/occlusion)
   - Quando a cena tiver muitos objetos, conferir se objetos fora da câmera/escondidos
     atrás de outros estão sendo descartados antes de desenhar.

8. ✅ (conferido 2026-10-14: os 3 sistemas e o ImGui criam o pipeline no construtor,
   antes do loop) Stutter de compilação de pipeline/shader
   - Garantir que todo VkPipeline necessário é criado antecipadamente (carregamento/início),
     nunca na primeira vez que é usado durante o gameplay de verdade.

9. Redundância de cálculo aceitável hoje, revisar se virar hot path
   - Ex: findQueueFamilies rodando mais de uma vez na inicialização (pickPhysicalDevice,
     createLogicalDevice, createCommandPool). Não otimizar agora, só revisitar se algo
     parecido aparecer rodando por frame, não só na inicialização.

10. ✅ (feito 2026-10-14) Desenhar durante o arrasto de redimensionamento (Windows)
   - Feito: refresh callback da CrsWindow + lambda drawFrame no FirstApp::run, ligado só onde
     platform::needsRedrawDuringResize(); e o beginFrame passou a tentar adquirir de novo
     depois de recriar a swap chain (era o motivo real do congelamento).
   - LIMITES que ficaram (revisitar):
     * só sai frame quando o tamanho muda: segurar a borda parada, ou MOVER a janela pela
       barra de título (também é loop modal do Windows), ainda congela e pausa o jogo.
       Solução definitiva: thread de render separada da thread de eventos (Unreal/Unity);
       meio-termo só Windows: WM_TIMER durante o loop modal, no crs_platform_windows.cpp.
       Fazer quando o jogo/editor precisar rodar sem pausar.
     * ✅ (2026-10-19) drawFrame virou método do FirstApp; o refresh callback é [this]{ drawFrame(); }.
     * frames do refresh callback não passam pelo limitador de FPS (inofensivo).
   (texto original do item abaixo)
   - No Windows, o SO trava o loop principal (glfwPollEvents) durante o arrasto de
     redimensionar a janela — drawFrame() não roda até soltar o mouse, então a imagem
     "congela" durante o arrasto (só atualiza no final). No Linux/macOS isso normalmente
     não acontece, porque o loop de eventos deles não bloqueia da mesma forma.
   - Correção: chamar drawFrame() (ou equivalente) de dentro do próprio
     framebufferResizedCallback, já que esse callback continua sendo chamado pelo SO
     mesmo com o loop principal travado.
   - Exige dar a CrsWindow uma forma de acionar FirstApp::drawFrame() sem quebrar a
     separação engine/jogo (hoje CrsWindow não conhece FirstApp de propósito) — por
     exemplo, guardando um std::function/callback que FirstApp registra.
   - Confirmado que não atrapalha portabilidade pra Linux: o mecanismo em si (GLFW +
     Vulkan) é multiplataforma; no Linux só ficaria redundante (desenha um pouco mais
     que o necessário durante o resize), sem quebrar nada.

FASE 3 — Varredura final de segurança/correção (fazer por ÚLTIMO, é o filtro final)
===============================================================================

11. Ponteiros pendurados (dangling pointers)
    - Procurar por qualquer struct que guarda um ponteiro/referência pra um campo dele mesmo
      (ex: algo.ponteiro = &algo.outroCampo) e que depois é copiado ou retornado por valor.
    - Bug já identificado: PipelineConfigInfo::viewportInfo (pViewports/pScissors apontando
      pra viewport/scissor do mesmo struct, dentro de defaultPipelineConfigInfo, que retorna
      por valor) — já corrigido, mas é exatamente o tipo de bug que as Fases 0-2 podem
      reintroduzir sem querer, por isso essa checagem vem depois delas.
    - Achado na Fase 1 (2026-10-13): SimpleRenderSystem::materialSets usa o ENDEREÇO da
      CrsTexture como chave. Se um modelo for destruído durante o jogo, o descriptor set
      fica apontando pra uma image view destruída, e uma textura nova alocada no mesmo
      endereço herdaria o set velho. Hoje não acontece (modelos vivem o programa todo);
      vira bug real quando houver carregar/descarregar de cena. Junto: os sets do pool de
      materiais (MAX_MATERIALS = 100) nunca são devolvidos.

12. Ordem de destruição dos recursos Vulkan
    - Em cada destrutor (CrsDevice, CrsSwapChain, CrsPipeline, etc.), conferir se a ordem
      de destruição é o inverso exato da ordem de criação.
    - Achado na Fase 1 (2026-10-13): SimpleRenderSystem e PointLightSystem fazem
      vkDeviceWaitIdle no destrutor, ShadowRenderSystem não. O FirstApp::run já espera no
      fim do loop, mas se der exceção no meio os sistemas são destruídos sem essa espera.
      Decidir um lugar só pra esperar a GPU (ex: um guard no run) em vez de cada destrutor.

13. Vazamento de recurso (resource leak)
    - Todo vkCreate*/vkAllocate* deve ter um vkDestroy*/vkFree* correspondente em algum lugar.
    - Conferir se todo caminho de erro (throw) não deixa recurso já criado sem limpar.
    - Achados na Fase 1 (2026-10-13): loadGltf não chama cgltf_free se der exceção no meio
      do loop (unique_ptr com deleter resolve); construtores da CrsTexture não liberam os
      pixels do stb se o upload der throw; VkResult sem checagem em vkMapMemory/
      vkQueueSubmit/vkAllocateCommandBuffers (crs_buffer, endSingleTimeCommands).
    - Entrada não confiável: loadGltf não chama cgltf_validate — um .glb malformado pode
      fazer o accessor ler fora do buffer. Validar logo depois do cgltf_load_buffers.

14. Consistência de RAII
    - Conferir se toda classe que adquire um recurso (Vulkan, memória, arquivo, etc.) em
      algum construtor libera esse mesmo recurso no destrutor correspondente.
    - Prestar atenção especial em classes adicionadas mais pra frente no projeto: se algum
      recurso novo foi alocado com "new"/malloc solto (sem RAII, sem ponteiro inteligente)
      em vez de seguir o padrão já estabelecido (CrsWindow, CrsDevice, CrsPipeline,
      CrsSwapChain).

15. ✅ (resolvido 2026-10-12: renderFinishedSemaphores agora é por imagem da swap chain,
    indexado pelo imageIndex; validation layer sem nenhum aviso) Reuso de semáforo do swap chain (aviso real já visto no console)
    - Aviso da validation layer: "vkQueueSubmit(): pSignalSemaphores[0] ... may still be in
      use by VkSwapchainKHR" — acontece porque imageAvailableSemaphores/renderFinishedSemaphores
      são indexados por currentFrame (0/1, de MAX_FRAMES_IN_FLIGHT) em vez de pelo índice real
      da imagem adquirida (0/1/2, de imageCount()). Padrão "clássico" de tutorial, pego por
      validation layers mais recentes/rigorosas.
    - Correção sugerida pela própria mensagem: um semáforo por imagem do swap chain, indexado
      pelo imageIndex devolvido em acquireNextImage, não por currentFrame.
    - Não trava o programa (é aviso, não erro fatal) — não veio de vkDeviceWaitIdle nem de
      ordem de destruição, esses dois já foram corrigidos.

4. Terreno básico, sem streaming ainda (heightmap simples, mundo pequeno o
   suficiente pra não precisar de streaming/LOD de cara). Ganha utilidade dupla
   com o item 3: sobrevoar/inspecionar em modo editor, andar de verdade em modo jogo.
   Desenho pedido pelo usuário (2026-10-29), em C++ (engine/terrain), dados em assets/terrains/:
   4.1. Terreno em PEDAÇOS (tiles): o usuário diz só o tamanho total; a engine cria quantos
        pedaços forem precisos, cada um com o próprio heightmap de resolução fixa (ex: 257x257
        amostras por pedaço) — a resolução não cai com o tamanho do mundo. Cada pedaço carrega
        e descarrega sozinho (já prepara o streaming / carregamento por setor).
        A engine cuida das divisas: a borda é a MESMA amostra nos dois pedaços vizinhos (por isso
        257 = 256 + 1); o pincel que passa na divisa escreve nos dois; a normal da borda usa os
        vizinhos (sem costura na luz). Com LOD por pedaço, vizinhos de resoluções diferentes
        precisam de "saias" ou costura pra não abrir rachadura.
        Colisão: terrain.heightAt(x, z) acha o pedaço e interpola (física + Python).
   4.2. Pintura de camadas (texture splatting): splat map RGBA por pedaço (4 camadas por imagem:
        terra, grama, estrada...), pincel no editor, shader mistura pelas cores. Mesma regra de
        divisa do 4.1. Python: terrain.layerAt(x, z) (som de passo, poeira).
   4.3. Grama procedural (scattering): mapa de densidade pintado; folhas espalhadas pela engine
        com instancing (milhares numa chamada) e vento no vertex shader. Perto: folhas de verdade.
        LONGE (ideia do usuário): troca as folhas por um ruído/tom de grama no próprio shader do
        terreno, onde a densidade diz que tem grama — mantém a aparência sem o peso dos objetos;
        a passagem perto->longe se mistura aos poucos (sem linha visível).
        Referência (vídeo sobre florestas da Ubisoft, visto pelo usuário em 2026-10-29): em 4K o
        "pop" de grama surgindo do nada é muito visível, porque sem névoa densa dá pra ver longe.
        Por isso o ruído JÁ está lá antes (mesma densidade e cor da grama) e a grama vai entrando
        no lugar dele aos poucos — o olho vê "a mesma coisa ficando mais detalhada", não algo
        aparecendo. Detalhes pra fazer a troca sumir:
        - o ruído usa o MESMO mapa de densidade e a mesma cor média das folhas;
        - folhas entram crescendo do chão (escala 0 -> 1) ou por dither, nunca de uma vez;
        - quanto mais longe, menos folhas e mais largas (afinar a densidade com a distância);
        - a distância de troca depende da resolução/qualidade gráfica (4K pede mais longe).
   Ordem: 4.1 -> 4.2 -> 4.3 (a pintura pinta no terreno; a grama usa o pincel e a altura).
   Combinado: Python (3.4) antes, terreno logo depois.

6.1. Máscara de opacidade do corpo (anotado 2026-10-18, a partir de uma pesquisa do
   usuário) — complementa o item 6, não substitui: resolve a pele do corpo atravessando
   a roupa (clipping) sem fatiar a malha do personagem.
   - O personagem continua uma malha única (pele contínua, UV estável). Cada item
     equipável traz, além da malha dele, uma máscara em tons de cinza na MESMA UV do
     corpo: preto = coberto pela roupa (o pixel do corpo é descartado), branco = pele
     visível (inclusive rasgos/aberturas da roupa).
   - No fragment shader do corpo: amostra a máscara e faz `discard` se for quase preto,
     antes da iluminação. Mudar raça/pele = trocar só a textura do corpo; roupa rasgada
     = editar só a máscara, sem remodelar nem refazer rig.
   - Ao equipar/desequipar, combina as máscaras dos itens numa só (o mínimo de cada
     pixel: coberto por qualquer item = coberto). Só refaz quando o equipamento MUDA,
     não a cada frame.
   - Cuidados pra quando for implementar: (1) `discard` atrapalha o teste de profundidade
     antecipado da GPU, então usar só no pipeline do corpo, não em tudo; (2) o passe de
     sombra pode ignorar a máscara (a sombra da pele escondida fica embaixo da roupa);
     (3) os bindings do exemplo da pesquisa não batem com os da engine (set 0 binding 2
     já é o buffer de luzes; texturas de material ficam no set 1) — encaixar no layout real.
   - Depende dos itens 5 (animação esquelética) e 6 (equipamento por skinning compartilhado).

6.2. Partes do corpo que ligam/desligam (anotado 2026-10-18, incremental, depois do 6.1) —
   o corpo dividido em poucas regiões grandes (ex: tronco, braços, pernas, pés) que um item
   pode desligar inteiras, como os "geosets" do WoW: uma armadura que cobre o tronco todo
   desliga o tronco, e ele nem é processado (com a máscara, a pele escondida ainda passa
   pelo skinning e só é descartada no fim). A máscara do 6.1 continua cuidando das bordas,
   rasgos e aberturas. Custa alguns draw calls a mais por personagem (barato no Vulkan;
   só pesa com muitos personagens na tela).
   - Requisito pra não quebrar efeitos de pele: as partes são só um corte da MESMA malha —
     mesma UV global, mesma textura e mesmo material do corpo. Assim um efeito calculado no
     shader a partir da UV (ex: maldição se espalhando, ver abaixo) atravessa as costuras
     entre partes sem emenda.
   - Ideia de efeito compatível (maldição que se espalha): uma textura de "caminho" na UV
     do corpo, em tons de cinza = momento em que cada ponto é tomado (o artista pinta por
     onde ela avança, ex: da mão subindo pelas veias); o shader compara com um único valor
     de progresso (0 a 1) que o jogo aumenta com o tempo. Nada de editar textura na CPU.
   - Evitar costura visível entre as partes (problema que o usuário já teve no UPBGE: linha
     serrilhada na divisão, mesmo parado, que sumia no editor). Causa: cada parte era um
     objeto separado com vértices de borda duplicados; a mesma posição calculada por dois
     caminhos (matrizes diferentes) arredonda diferente e abre uma fresta de fração de pixel,
     que o anti-aliasing do viewport escondia. JEITO DE IMPLEMENTAR: as partes NÃO são
     objetos nem malhas separadas — é um objeto só, com UM buffer de vértices, e cada parte
     é só um intervalo da lista de índices (desligar uma parte = não desenhar aquele
     intervalo). O vértice da borda é o mesmo nas duas partes: uma transformação só, mesmos
     pesos e mesma normal, e a GPU encaixa os triângulos sem fresta. Na arte: pesar e calcular
     normais no corpo inteiro, marcar as regiões (ex: um material ou grupo por parte só pra
     separar os índices no export), e cortar onde a roupa costuma cobrir (pulso, tornozelo,
     pescoço, cintura).
     Origem: o corpo, as partes e os itens rigados (item 6) usam TODOS a mesma origem, a do
     esqueleto/armature (no UPBGE o usuário movia a origem de cada parte pro centro dela com
     "Origin to Geometry" — isso dá a cada parte uma matriz diferente e foi o que abriu a
     fresta). Origem no centro é ótimo pra objeto solto (caixa, porta), não pra peça de personagem.

7. Sistema de combate — depende do item 5, se beneficia do item 6 já existir
   (feedback visual de arma equipada, etc.).

8. Progressão de equipamento/status (upar, melhorar itens) — mistura de dados e
   lógica de jogo, pode crescer em paralelo com o item 7.

9. Streaming de mundo + LOD — só quando o terreno/conteúdo real for grande o
   suficiente pra doer em performance. LOD reduz detalhe do que está longe mas
   carregado; streaming evita até carregar o que está muito longe. As duas
   técnicas são necessárias juntas pra um mundo aberto de verdade (nenhuma
   substitui a outra).
   LOD de modelos (decidido 2026-10-29): híbrido.
   - Automático por padrão: ao importar, a engine gera os níveis simplificando a malha
     (biblioteca meshoptimizer, a mesma que o Godot 4 usa). Bom pra pedras, props, prédios.
   - Manual quando o automático estragar: níveis feitos no Blender dentro do mesmo .glb
     (ex: nomes Arvore_LOD0, Arvore_LOD1...) substituem os gerados.
   - Último nível pra vegetação: impostor (billboard) — a engine fotografa o modelo de vários
     lados numa textura (o mesmo "desenhar fora da tela" das miniaturas do navegador de assets)
     e desenha em 2 planos cruzados; versão melhor depois: impostor octaédrico.
     Árvores precisam disso porque simplificar folhas (planos finos) deixa a copa rala.
   - Troca de nível pelo tamanho na tela, com mistura (dither) pra não "estalar".
   Paisagem de longe (objetivo do usuário, 2026-10-29): do castelo/vila no alto da cordilheira, olhar
   o desfiladeiro e ver um cenário bonito e "completo" (como Anor Londo no Dark Souls ou o avião no
   GTA V), feito de ilusão barata. Técnicas, da mais simples à mais trabalhosa:
   - Perspectiva aérea (não é névoa de guerra): o longe fica mais claro e azulado pela atmosfera;
     é o que dá sensação de escala. Um ajuste no shader, barato.
   - Terreno de longe: pedaços distantes com bem menos pontos; o além-desfiladeiro pode ser só isso.
   - Grama longe = ruído no shader do terreno (item 4.3); árvores longe = impostores; floresta
     inteira longe = poucos impostores grandes.
   - HLOD (LOD hierárquico): muitos objetos longe (uma vila, o castelo visto de baixo) viram UMA
     malha simplificada só, com uma textura; a Unreal faz assim no World Partition, o GTA tem os
     "SLOD". Uma chamada de desenho no lugar de centenas.
   - Cenário de fundo (backdrop): o que NUNCA dá pra alcançar (montanhas além do mapa) é só uma
     malha de fundo ou o céu pintado — nunca tem versão "de verdade".
   - À noite: luzes de cidade longe viram pontinhos brilhantes (sprites), sem luz de verdade.
   Regra: o que dá pra alcançar tem a cadeia de LOD completa e volta a ficar real ao chegar perto
   (streaming carrega antes de chegar, com folga pra queda rápida); o que não dá, é só fundo.

10. Editor de terreno dentro da própria engine (opcional, avançado) — só faz
    sentido depois dos itens 3 (modo editor já existe) e 4 (terreno já existe).
    Motivo de preferir isso a esculpir no Blender e exportar: o formato de dados
    do terreno precisa bater com o esquema de chunk/streaming da própria engine
    desde a origem (esculpir fora e importar exigiria uma etapa extra de
    conversão/fatiamento depois); editar dentro da engine também dá referência
    de escala real (personagem do lado) e a iluminação/renderização verdadeira
    do jogo, coisa que o viewport do Blender não reproduz fielmente. Também evita
    costura visível entre pedaços de terreno editados isoladamente em arquivos
    separados. Alternativa mais barata: esculpir no Blender e importar, aceitando
    a fricção extra — válido se esse editor nunca virar prioridade.

11. Projetos (longo prazo, versão 2.0/3.0 — pedido do usuário 2026-10-30) — a engine abre
    PROJETOS: cada projeto é uma pasta com o próprio assets/ (modelos, sons, texturas, cenas,
    scripts e componentes Python) e um arquivo de projeto (nome, cena inicial, configurações).
    Abrir um projeto = tudo passa a ser lido da pasta dele (o sys.path do Python também).
    "Novo projeto": escolhe uma pasta e a engine monta a estrutura inteira dentro dela
    (assets/{models,sounds,textures,scenes,scripts,components}, arquivo de projeto, cena vazia
    com câmera e luz). O projeto atual (o de exemplo da engine) não precisa disso agora.
    Projeto de exemplo (pedido do usuário 2026-10-30): o instalador da engine cria
    automaticamente o projeto de exemplo (o de hoje: personagem, câmera, animações, scripts),
    pra quem está aprendendo abrir e ver como um projeto deve ser. Ele é instalado como um
    projeto comum, numa pasta do usuário (ex: Documentos/CRSDK/Exemplo), não dentro da pasta
    da engine: assim pode ser mexido à vontade, e reinstalar/atualizar a engine não apaga o que
    a pessoa mudou. Bom ter: "Restaurar projeto de exemplo" no menu, que cria uma cópia nova.
    Cuidados a tomar desde já, pra não ter que desfazer depois:
    - caminhos de asset relativos à raiz do projeto, nunca absolutos (a cena salva já usa
      "assets/..."; hoje os caminhos fixos ficam só no first_app.cpp);
    - separar o que é da ENGINE (assets/editor: gizmos de câmera/empty, shaders, o crsdk.pyi)
      do que é do PROJETO: os da engine ficam do lado do .exe e servem pra todo projeto;
    - quando chegar a hora, os caminhos passam por um lugar só (ex: project.path("models/x.glb"))
      em vez de cada arquivo montar o próprio "assets/...".
